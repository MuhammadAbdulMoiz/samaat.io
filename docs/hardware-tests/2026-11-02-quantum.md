## Bugs and discrepancies

### 1. Fixed: a device first seen without a battery level never got one

`WindowsDeviceSource.DiscoverAsync` cached each device by ID and skipped any it had already built. A device that Windows had no battery level for at first discovery (`OsBatteryFeature.CreateAsync` returned null) kept no battery feature forever, contradicting STATUS.md ("appears on the next Refresh") and docs/modules/battery.md.

Fix: a cached device with no features is disposed and rebuilt on the next discovery. Found by reading the code; not reproduced on this hardware (both headsets already had a stored level). No unit test: `WindowsDeviceSource` calls WinRT directly and the repo has no Windows-platform test project or seam for it; adding one would be a larger refactor than the fix.

### 2. Open: stale battery shown for a disconnected device

Windows keeps the last level (80) on the Hands-Free AG node after the headset disconnects. Settings hides it; Samaat shows **80%** on the device card and in the CLI. The capability row correctly says "Device disconnected", but the card's percentage and bar read as current. Suggest the device card dims or hides the percentage (or shows its age) when disconnected. This is a UI/Core presentation choice, so it is written up rather than changed here.

## Bluetooth service scan (read-only)

Throwaway WinRT probe (not in the repo): dump the raw SDP records and RFCOMM services, scan BLE for 15 s, then open each serial channel and **listen only** (nothing written).

Class of Device `0x240404` (Audio/Video, rendering + audio services). Chip vendor: **Jieli** (every service name is `JL_*`, VID `0x05D6`).

| SDP record | Service class | Transport | Name | Notes |
|---|---|---|---|---|
| 0x10001 | A2DP sink `110B` | L2CAP PSM 0x19 (AVDTP 1.3) | `JL_A2DP` | features 0x1 |
| 0x10002 | AVRCP controller `110E/110F` | AVCTP 1.4 | | AVRCP 1.5, features 0x1 |
| 0x10005 | AVRCP target `110C` | AVCTP 1.4 | | features 0x2 |
| 0x10003 | Hands-Free `111E` | RFCOMM ch 4 | `JL_HFP` | HFP 1.8, features 0x3F |
| 0x10004 | **SPP** `1101` | RFCOMM ch 1 | `JL_SPP` | |
| 0x10011 | **Custom** `fe010000-1234-5678-abcd-00805f9b34fb` | RFCOMM ch 10 | `JL_SPP` | Believed to be Jieli's RCSP control channel (unconfirmed) |

- No BLE device at the classic address, and no matching BLE advertisements in 15 s.
- Both serial channels accept a connection from the PC without extra pairing.
- SPP (ch 1): silent for 8 s.
- Custom channel (ch 10): pushed one unsolicited 24-byte frame on connect:
  `030100030000000302000608050403020103030003FFFFFF`. Not decoded yet.

### Read-only RCSP queries (same day)

Framing and the Jieli auth cipher were taken from [buds-sniffer](https://github.com/Neisvestney/buds-sniffer) (MIT), which reads L/R/case battery from a Jieli earbud with the **same VID/PID `0x05D6`/`0x000A`** over BLE `AE00`. The C# port of the cipher passed its known-answer test. Only these were sent: `GetTargetInfo` (`FE DC BA C0 02 00 05 00 FF FF FF FF EF`) and the raw auth step 1 (`00` ‖ 16 random bytes).

| Channel | Result |
|---|---|
| Custom ch 10 | Same 24-byte greeting on every connect (static, not RCSP-framed). **No reply** to `GetTargetInfo` or auth step 1 in 3 s each, nothing more in a 20 s listen. |
| SPP ch 1 | Silent; **no reply** to either. |
| BLE at the classic address (public and random) | No device. |
| BLE scan, 20 s, for company `0x05D6` / service `AE00` | One Jieli advertiser, `C0:06:47:FA:4B:C9`, RSSI −78, payload `0200810052C00647FA4BC9804344C00647FA4BC9…`. Not linked to these earbuds (different address, weak signal); possibly another Jieli device nearby. |

**Case-lid BLE scan.** 90 s active scan for company `0x05D6`, service `AE00` or name "Quantum", while the owner closed the buds in the case and reopened it next to the PC. `BluetoothDevice.ConnectionStatusChanged` fired as expected (WinRT level, the same event `WindowsEarbudDevice` uses): Disconnected at 13:25:01 when the lid closed, Connected again at 13:25:14 when it opened (automatic reconnect). **No new BLE advertiser** appeared before, during or after. The `C0:06:47:FA:4B:C9` beacon sent the same bytes throughout, unaffected by the lid, so it is not these earbuds. An earlier 90 s attempt caught no lid action and is discarded.

So these earbuds do not speak RCSP the way the buds-sniffer earbuds do, at least not over classic Bluetooth while connected to the PC. The ch 10 greeting looks like a different, unknown protocol; decoding it without a reference app would mean guessing commands, which is not read-only, so it was stopped there.

**Meaning:** the earbuds have a vendor channel (ch 10), but it does not answer the known Jieli RCSP commands. Per-bud battery, ANC/transparency and other settings are reachable only if its protocol can be identified. Without a vendor app to observe, that is unlikely; Basic support (Windows battery) is the realistic ceiling for this model unless new evidence turns up (vendor-adapter work, PLAN §13 Q1). Firmware update (OTA) commands on this channel must never be sent; they can brick the earbuds.

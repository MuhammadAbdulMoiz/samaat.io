# Repository audit and fixes, 2026-11-10

**Status:** branch `fix/audit-hardening`, from `dev` at `9f7255b`. Committed locally, not pushed. · **Date:** 2026-11-10

## Why this work happened

A full audit of the repository: architecture, security, reliability, tests, user experience and production readiness. The rule for this pass was to fix what is unreliable before adding anything, with small changes and no rewrites.

**Baseline:** 0 build warnings, 1,319 tests passing, no vulnerable NuGet packages (including transitive ones). **After:** 0 warnings, 1,351 tests (Core 340, Protocols 423, App 428, Handoff 131, Platform.Windows 29).

**How it was reviewed:** three read-only audits (phone link security; core, platform and protocol reliability; app layer and UX), then a fix plan and the finished implementation each reviewed by Codex. The plan passed on its second round after four findings were accepted; the implementation passed on its second round after three.

## Overall condition

The project is in good shape for its age. The layering is enforced by tests, every protocol parser is length-checked, writes are confirmed and rolled back, and the phone link's cryptography is sound: keys per direction, counter nonces, a commit-then-reveal pairing with a constant-time comparison, a 256 KB frame cap, and at most four handshakes at once. The audit found no Critical issue. The problems were at the edges: starting, exiting, error paths, and what happens when earbuds come back.

## Fixed

| # | Severity | Problem | Fix |
|---|---|---|---|
| 1 | High | **Two copies could run at once.** Each had its own tray icon and phone-link listener and wrote the same settings and paired-phone files; the last writer won. | A second launch brings the running window forward and exits (`SingleInstance`). `--multi-instance` skips the guard for development. |
| 2 | High | **Quitting didn't wait for cleanup.** Disposal hung off an async handler the app lifetime didn't wait for, so the audio share, the phone listener and the Bluetooth handles could be cut off mid-way. | One cleanup that runs once on every exit path, waits up to 3 s, and disposes each service on its own so one failure doesn't skip the rest. |
| 3 | High | **An exception on the UI thread ended the app.** Only the last-chance handlers logged it. | It is logged and shown as a toast; the startup and tray refreshes are guarded. |
| 4 | High | **One failing Bluetooth device hid every device.** A single COM error during discovery emptied the whole list until the next refresh. | Each paired device is read on its own; a failure is logged and only that device is skipped. |
| 5 | Medium | **Low-battery alerts for earbuds that aren't connected.** Windows keeps the last level, and a stale 12 % raised a toast and a system notification. | No alerts while disconnected. The last level is still shown, and the alert fires once the earbuds connect and are still low. |
| 6 | Medium | **Settings and paired phones could be written into the working directory.** On Linux without `~/.config` the data folder came back empty and the path became relative. Two such files had been committed at the repo root (a random id and an empty list; no key material). | `AppDataFolder` only accepts an absolute folder and falls back to the local data folder, then the temp folder. The stray `Samaat/` folder is removed and ignored. |
| 7 | Medium | **A cancelled Jieli restart silenced the earbuds.** Their later messages went to an inbox nobody read, so battery updates stopped. | The inbox is cleared on every path; disposal waits for a running restart. |
| 8 | Medium | **Saving settings could lose a save or leave an empty file.** A fixed temp file name collided under concurrent saves, and nothing was flushed before the swap. | A unique temp file per save, flushed to disk, with the swap serialised. |
| 9 | Medium | **Audio sharing could keep playing while the app said "Stopped".** A failure late in starting left the stream running. | The stream is retired on that failure. |
| 10 | Medium | **Leaks on failed device setup.** A Bluetooth device, GATT client or feature created before a failure was never released. Disposing a channel twice threw. | Everything created so far is released on failure; channel disposal is safe to repeat; disposing the source waits for a running refresh. |
| 11 | Low | **Phone link took unbounded text from the network.** A phone or beacon name could be up to 256 KB, and beacons with random ids grew a list without limit. | Names are cut to 64 characters, ids over 64 are ignored, the list holds 64 entries, and a malformed datagram can't stop the listener. |
| 12 | Low | **A cancelled send could break the encrypted session.** The frame counter had advanced but the frame was only half written. | Once a frame is sealed it is always written in full. |
| 13 | Low | **Internal error text went to the phone.** | The phone gets a fixed message; the detail goes to the log. |
| 14 | Low | **A damaged paired-phones file could stop the app starting,** and the next save overwrote it. | A bad entry is skipped and logged, and a corrupt file is kept as `phones.json.bad`. |
| 15 | Low | **Release workflow pasted the tag name into PowerShell,** and CI ran with the default token permissions. | The tag and version arrive through environment variables; CI's token is read-only. |
| 16 | Low | Silent failures: a dropped RFCOMM link, a refused notification subscription, an unreadable Windows battery value, an unknown command-line option. | Each is now logged. An unreadable battery value no longer throws inside a system callback. |

Also: the unused `Converters.EnabledOpacity` is removed, a [SECURITY.md](../../SECURITY.md) says how to report a problem, and the test counts in the README and STATUS are corrected.

## What was and wasn't verified

- **Verified by tests:** items 1 (on Windows), 2, 5, 6, 7, 8, 9, 11, 12, 13 and 14, plus the battery-value parsing in 16. The new tests for 7, 8, 9, 11, 12, 13 and 14 were watched failing before the fix.
- **Build-verified only:** items 4, 10 and the logging in 16 live in the Windows Bluetooth layer and need real earbuds. They change error paths only; what is sent to the earbuds, and in what order, is unchanged.
- **Not run:** the app itself. The second-launch raise, the tray's Quit and the exit cleanup were not tried end to end. Nothing was tried on a phone or on Linux.
- **Not confirmed:** whether Avalonia raises `ShutdownRequested` when the tray calls `Shutdown()`. The cleanup hangs off both that and `Exit`, so it runs either way.

## Not fixed

These were found and left, each for a stated reason.

| Severity | Problem | Why it was left |
|---|---|---|
| High | **RFCOMM drivers don't re-handshake after earbuds drop and return** (Nothing, Sony, Soundcore, Samsung, Bose). `DriverRetry.CanReuse` keeps the device whose session is dead, so noise control and EQ fail until Samaat restarts. Jieli and Fast Pair recover on their own. | The fix (mark the device stale on disconnect and rebuild it on reconnect) changes the reconnect path of drivers that were checked on hardware, and it can't be checked without earbuds. This is roadmap item 5 in [STATUS.md](../STATUS.md). |
| Medium | **The phone listener binds every network interface** while a phone is paired, so the pairing handshake is reachable on a public network too. | Narrowing the address risks breaking discovery on computers with several networks, and needs a phone to test. What an unpaired device can reach is already bounded. |
| Medium | A device that starts reporting battery after launch only appears on the next Refresh. | Refreshing on a timer re-opens failed drivers, each with an 8 s budget. Needs a cheaper "anything new?" check first. |
| Medium | Failures from the tray (a connect that didn't work) show as a toast in a window that may be hidden. | Needs the window's visibility in the view model; small, but a feature. |
| Medium | Closing the window hides the app in the tray with no first-time hint. | A feature, not a defect. |
| Low | An unanswered pairing prompt holds the pairing slot after the pairing window closes; a spoofed beacon can point a paired phone at the wrong address (it then fails to authenticate). | Nuisance only, and both need a phone to test. |
| Low | `LatestValueSender` has no timeout, so a setter that hangs would stall a slider. | No hang was shown; the fix belongs with reconnect handling. |
| Low | GitHub Actions are pinned to tags (`@v4`), not commit hashes. | Dependabot already updates them weekly; pinning is the owner's call. |
| Low | The largest classes (`PhoneLinkHost`, `DeviceViewModel`) and the two device databases are still as [ARCHITECTURE.md](../ARCHITECTURE.md#known-debt) describes. | Refactors with no user-visible gain; out of scope for a reliability pass. |

## Roadmap

1. **Reconnect handling for the RFCOMM drivers**, with the CMF Buds on the desk. It is the one High finding left and the most visible failure for a daily user.
2. **Run the phone handoff on a real phone**, then decide the listener's bind address and close the pairing slot with the window.
3. **A manual release check** that covers what tests can't: second launch, Quit from the tray, close to tray, start with Windows, a notification on a clean profile.
4. **Tray and background feedback:** system notifications for failures while the window is hidden, and a one-time "still running in the tray" hint.
5. **Auto-refresh** for devices that start reporting after launch, once discovery has a cheap path.
6. **Unify `DeviceCatalog` and `DeviceProfileDb`**, then split `PhoneLinkHost` and `DeviceViewModel`.
7. **Hardware evidence** for the ported drivers (Samsung, Soundcore, Sony), so entries can move to `verified`.

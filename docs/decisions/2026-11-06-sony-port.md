### Why two sources

SonyHeadphonesClient can only **set** the noise mode and virtual sound. Its README lists "display battery life and fetch existing settings" as not done, and none of its branches, nor the eight MIT forks checked (`semvis123`, `andro2157`, `jimzrt`, `pasical`, `zhichengg`, `jespinobe`, `someconfusednoises`, `aybruh00`), reads anything over the Sony protocol. A read-only port from it alone would have shown nothing. **The owner chose (2026-11-06)** to add the reads clean-room from Gadgetbridge's behaviour, as the plan's phase 2b allows. The message formats are written in Samaat's own words in [the protocol note](../protocols/sony.md); the code was written from that note by someone who didn't read Gadgetbridge. No Gadgetbridge code was copied or translated, so it isn't in `THIRD_PARTY_NOTICES.md`. Only SonyHeadphonesClient is, with its MIT notice.

## What was built

`src/Samaat.Protocols.Sony` (references Core and Transport only), driver id `sony-mdr`, registered once in `BuiltInDrivers`:

- **Framing** (ported): `3E … 3C`, escaping of `3C`/`3D`/`3E`, kind, sequence number, big-endian length, sum checksum; a reader that drops bad frames and caps an unfinished one at 2048 bytes.
- **Session** (clean-room): one command at a time; the headphones' ACK hands over the next sequence number; every message from the headphones is acknowledged.
- **Init:** `00 00`, sent twice at most. Only a v1 reply (4 bytes) continues; v2 headphones get no features.
- **Battery:** headset level, or left/right plus case, in percent with charging; a bud with level 0 shows as disconnected. Updated by the headphones' battery pushes.
- **Noise control:** the current mode (off, noise cancelling, ambient sound shown as transparency; wind noise reduction shows as noise cancelling), updated by pushes. Read-only.
- **Models**, 4 in `devices/sony/`: WH-1000XM3 and WH-1000XM4 (battery, noise mode), WF-1000XM3 (left/right/case battery, noise mode), MDR-XB950BT (battery only, a lead: it isn't in Gadgetbridge). The driver offers only what got a well-formed reply.

## Read-only for now

The owner's rule: **read-only until we have our own captures.** The shipped driver writes only init, the battery and noise queries, and ACKs; a test checks that nothing else is written. SonyHeadphonesClient's set command is ported and tested against fake channels, but only `new SonyDriver(allowWrites: true)` turns it on, and its mapping (noise cancelling = "ambient sound control off") comes from that app's UI, so it needs a capture before anyone turns it on. Turning noise control fully off isn't offered.

## What was tested

- Frame vectors computed by hand from the protocol note, and set-command vectors computed from SonyHeadphonesClient's serializer.
- The reader (split chunks, several frames, garbage, bad checksum, bad escape, oversized frame), the session's ACK and sequence handling, and the driver against scripted fake RFCOMM channels: v1 and v2 init replies, silence, each model's features, a disconnected bud, pushes, the read-only write allowlist, the write path with writes on, and disposal.
- Catalog: every `sony-mdr` entry is in the model table and the other way round, and sample names resolve to the right entry.
- **Not tested:** anything on real Sony headphones or a real RFCOMM link. Every frame is synthetic; there are no upstream test vectors to replay (SonyHeadphonesClient has no tests, and Gadgetbridge's can't be copied).
